# LSP Phase 1: Diagnostics for .qmui Files

## Goal

Show QuickMarkup diagnostics (parse errors, binding errors) in VS Code / Visual Studio
in real-time for `.qmui` files, sharing the diagnostic logic with the existing Roslyn
analyzer pipeline.

---

## Current Architecture

```
.qmui file → AdditionalFiles → Roslyn Analyzer (QuickMarkupAnalyzer)
                                   │
                          QuickMarkupParser  ← Roslyn-free (QuickMarkup.Language)
                                   │
                          QuickMarkupBinder  ← uses ITypeSymbol, Compilation
                                   │
                          CodeTypeResolver   ← deeply coupled to Roslyn
                                   │
                          QuickMarkupDiagnosticReporter → Roslyn Diagnostic
                                   │
                          IDE / dotnet build shows diagnostics
```

**Key dependencies:**

| Component | Roslyn dependency | Location |
|---|---|---|
| Lexer/Parser/AST | None | `QuickMarkup.Language/` |
| `CodeTypeResolver` | `Compilation`, `ITypeSymbol`, `INamedTypeSymbol`, etc. | `QuickMarkup.CodeAnalysis/CodeTypeResolver.cs` |
| `QuickMarkupBinder` | Uses `CodeTypeResolver` (indirect Roslyn dep) | `QuickMarkup.CodeAnalysis/Binders/QuickMarkupBinder.cs` |
| `QMDiagnostic` hierarchy | Nearly none (one type uses `FullNameWithoutAnnotation` from `Get.EasyCSharp`) | `QuickMarkup.CodeAnalysis/Binders/QMBinderError.cs` |
| `QuickMarkupDiagnosticReporter` | Outputs Roslyn `Diagnostic` | `QuickMarkup.SourceGen/QuickMarkupDiagnosticReporter.cs` |
| `IQuickMarkupLocationProvider` | Outputs Roslyn `Location` | `QuickMarkup.SourceGen/IQuickMarkupLocationProvider.cs` |

**Why .qmui diagnostics don't show well in editors today:**
- The `QuickMarkupAnalyzer` runs on `CompilationAction` for .qmui files (not `SyntaxNodeAction`)
- IDEs prioritize diagnostics on source files; .qmui is an `AdditionalText`, not a source file
- No real-time re-diagnostics on edit (only on build / compilation)

## Roslyn Workspace Loading Strategy

### What is MSBuildWorkspace?

`MSBuildWorkspace` (from `Microsoft.CodeAnalysis.Workspaces.MSBuild`) can open a `.csproj`
or `.sln` file and produce a fully-resolved Roslyn `Workspace` containing all
documents, references, and a `Compilation` with all types resolved.

```csharp
using MSBuildWorkspace workspace = MSBuildWorkspace.Create();
Project project = await workspace.OpenProjectAsync("path/to/project.csproj");
Compilation? compilation = await project.GetCompilationAsync();
// compilation.GetTypeByMetadataName("Microsoft.UI.Xaml.Controls.Button") → works!
```

This gives us the **exact same type resolution** as `dotnet build` or the IDE.

### Does it give us LSP "for free"?

**No, not at all.** MSBuildWorkspace gets us a `Compilation` — the same object the
existing analyzer uses. That's one piece of the puzzle. We still need to build:

1. **The LSP protocol server** — handle JSON-RPC, manage documents, publish diagnostics
2. **The diagnostic pipeline** — parse .qmui → bind against compilation → convert to LSP types
3. **Incremental re-diagnostics** — re-run on each keystroke without reloading the workspace
4. **Project-to-file mapping** — given a .qmui file path, find the right `.csproj`

### How hard is it?

**MSBuildWorkspace itself is easy to use** (~20 lines of code to load a project).
But the challenges are:

#### Challenge 1: Finding the project from a .qmui path
A .qmui file lives at e.g. `src/MyPage.qmui`. We need to find the owning `.csproj`.

**Decision:** Use the VS Code workspace root folder (from `initialize` params) as
the project location. Scan for `*.csproj` inside it. If none found or workspace
root not available, fall back to **syntax-only diagnostics** (no type resolution).

#### Challenge 2: MSBuildWorkspace reliability
MSBuildWorkspace can fail if:
- The SDK/resolution workload isn't installed
- The project uses custom MSBuild props/targets that aren't available
- It's slow on large solutions (5-30 seconds initial load)

**Fallback chain:**

1. Try MSBuildWorkspace to load `.csproj` → full type resolution
2. If that fails, try AdhocWorkspace with manual document/project setup → partial type resolution
3. If both fail, fall back to **syntax-only diagnostics** (lexer/parser errors only, no binding)

**Other mitigations:**
- Show a status message while loading
- Cache the workspace across edits (reuse, don't reload)

#### Challenge 3: Performance on each keystroke
Parsing + binding a .qmui file against a full Roslyn compilation on every keystroke
can be expensive (50-200ms). For a good UX, we need to debounce.

**Mitigation:**
- Debounce diagnostics (e.g., 300ms after last edit)
- The parse+bind pipeline itself is fast — the bottleneck is Roslyn symbol resolution
- `CodeTypeResolver` caches type lookups (`Cache` dictionary), so repeated lookups are fast

**Crucial insight: The Compilation does NOT change on .qmui edits.**
Editing a `.qmui` file only changes the markup content — the C# source files and `.csproj`
are untouched. This means:

1. MSBuildWorkspace is loaded **once** and the `Compilation` is cached
2. On every keystroke in `.qmui`: re-parse content + re-run binder against the **same cached Compilation**
3. No need to re-load the workspace on `.qmui` edits
4. Only re-load if `.csproj` or `.cs` files change (detected via file watcher)

This is fundamentally different from the Roslyn analyzer pipeline, where every keystroke
in any file can trigger a new Compilation. In the LSP, the Compilation is stable across
.qmui edits, making per-keystroke diagnostics cheap (~5-50ms).

#### Challenge 4: Keeping the workspace fresh when C# changes
If the user edits a C# file that changes types used by the .qmui file, the cached
Compilation becomes stale. MSBuildWorkspace doesn't auto-update.

**What doesn't need reloading:**
- Editing `.qmui` itself → just re-parse + re-bind against cached Compilation (fast)
- Adding/removing `.qmui` files → no impact on Compilation

**What does need reloading:**
- Editing a `.cs` file that changes a type used by `.qmui` markup
- Adding/removing NuGet packages (changes `.csproj`)
- Adding/removing project references

**Mitigation for Phase 1:**
- Watch `.csproj` files in the workspace for changes → reload MSBuildWorkspace
- Accept that C#-only edits may produce stale diagnostics momentarily
- User can always rely on `dotnet build` for ground truth
- For Phase 2, add `.cs` file watcher with debounced workspace reload

### Overall Difficulty Rating: 4/10

The Roslyn workspace part is well-documented and straightforward. The real work is
building the LSP server infrastructure (protocol handling, document management,
diagnostic publishing). The diagnostic reuse is almost free.

### Agent B: LSP Diagnostic Converter + QmuiDiagnosticService

**Goal:** Build the pipeline that converts QuickMarkup binder errors into LSP
diagnostic objects. This is the core logic — no OmniSharp or workspace dependency
at the converter level.

**Estimated effort:** 1.5 days
**Prerequisites:** Agent A (project structure, namespace conventions)
**Can run in parallel with:** Agent C, Agent D

**Deliverables:**

1. **`LspDiagnosticConverter`** — maps `QMDiagnostic` → OmniSharp `Diagnostic`

   Full port of `QuickMarkupDiagnosticReporter.cs` (lines 13–155) but outputting
   OmniSharp's `Diagnostic` type with `Range`, `Severity`, `Message`, `Code`, `Source`.

   Key difference: input position comes from `QuickMarkupQmuiLocationProvider`-style
   logic (AST node start/end → line/character), not Roslyn `Location`.

```csharp
// Diagnostics/LspDiagnosticConverter.cs
static class LspDiagnosticConverter
{
    public static Diagnostic Convert(
        QMDiagnostic qmDiag, AST? node, string sourceText,
        string sourceName = "QuickMarkup"
    );
}
```

2. **`PositionConverter`** — maps `Get.PLShared.Position` (Line, Char) → LSP `Position`

   Both are 0-based, so this is a direct struct conversion.

3. **`QmuiDiagnosticService`** — orchestrates the full pipeline:

   Creates a new `QuickMarkupLexer` + `QuickMarkupParser` on each call (no caching needed
   — parser creation is negligible cost vs. Roslyn type resolution).

```csharp
// Diagnostics/QmuiDiagnosticService.cs
class QmuiDiagnosticService : IQmuiDiagnosticService
{
    public QmuiDiagnosticService(IRoslynWorkspaceManager workspaceManager);
    
    public async Task<IReadOnlyList<Diagnostic>> GetDiagnosticsAsync(
        string filePath, string content, CancellationToken ct)
    {
        // Step 1: Parse .qmui content (new lexer + parser per call — cheap)
        var lexer = new QuickMarkupLexer(new StringTextSeeker(content));
        var tokens = lexer.GetTokens();
        QuickMarkupSFC sfc = new QuickMarkupParser().Parse(tokens, out var parseErrors);
        
        // Step 2: Get compilation from workspace
        var compilation = _workspaceManager.Compilation;
        if (compilation is null)
            return LspDiagnosticConverter.ConvertParseErrors(parseErrors, content);
        
        // Step 3: Extract target info from parsed SFC (same logic as AnalyzeQmuiFile)
        var ns = sfc.Namespace?.Name ?? "";
        var typeName = sfc.ClassDeclaration?.Name ?? "";
        if (string.IsNullOrEmpty(typeName))
            return LspDiagnosticConverter.ConvertParseErrors(parseErrors, content);
        
        // Step 4: Resolve type symbol in compilation
        var fullName = string.IsNullOrEmpty(ns) ? typeName : $"{ns}.{typeName}";
        var typeSym = compilation.GetTypeByMetadataName(fullName);
        if (typeSym is null)
            return LspDiagnosticConverter.ConvertParseErrors(parseErrors, content);
        
        // Step 5: Bind
        var resolver = new CodeTypeResolver(compilation, sfc.Usings, ns);
        var binder = new QuickMarkupBinder(resolver, failFast: false);
        binder.Bind(sfc.Template, typeSym);
        binder.BindRefDeclarations(sfc.Refs, typeSym);
        
        // Step 6: Convert binder diagnostics + parse errors to LSP
        return LspDiagnosticConverter.ConvertAll(
            binder.Diagnostics, parseErrors, sfc, content
        );
    }
}
```

### Agent E: OmniSharp Handlers + Integration

**Goal:** Wire everything together — implement the OmniSharp handlers that react
to document events, call `QmuiDiagnosticService`, and publish diagnostics back
to the editor.

**Estimated effort:** 1.5 days
**Prerequisites:** Agent B (QmuiDiagnosticService), Agent C (RoslynWorkspaceManager)
**Cannot start until:** Both B and C are complete

**Design decisions for this agent:**

| Question | Decision | Rationale |
|---|---|---|
| SyncKind | `Full` (not Incremental) | .qmui files are small. OmniSharp sends full text on every change. No content-tracking dictionaries needed. |
| OmniSharp API discovery | Write closest match, fix compiler errors | OmniSharp 0.19.x API is stable; iterating on compile errors is faster than researching exact signatures upfront. |
| Debounce + close interaction | Don't cancel pending — just publish empty on close | On close, publish empty `Container<Diagnostic>` to clear squigglies. In-flight debounce tasks produce stale results but client shows latest (empty) so it's correct. |
| Handler tests | Smoke test only | Verify server builds and starts. Handler integration tests (mock pipelines) add little value vs. effort in Phase 1. |

**Deliverables:**

1. **`QmuiDidOpenHandler.cs`** — implements `IDidOpenTextDocumentHandler`

   Inject `IQmuiDiagnosticService` and `ILanguageServer` (or `ITextDocumentLanguageServer`)
   via constructor. On `Handle`, call the service and publish via
   `_server.TextDocument.PublishDiagnostics(...)`.

```csharp
class QmuiDidOpenHandler : IDidOpenTextDocumentHandler
{
    readonly IQmuiDiagnosticService _diagnostics;
    readonly ILanguageServer _server;
    
    public QmuiDidOpenHandler(IQmuiDiagnosticService diagnostics, ILanguageServer server)
    {
        _diagnostics = diagnostics;
        _server = server;
    }
    
    public async Task<Unit> Handle(DidOpenTextDocumentParams request, CancellationToken ct)
    {
        var results = await _diagnostics.GetDiagnosticsAsync(
            request.TextDocument.Uri.LocalPath,
            request.TextDocument.Text,
            ct
        );
        _server.TextDocument.PublishDiagnostics(new PublishDiagnosticsParams
        {
            Uri = request.TextDocument.Uri,
            Diagnostics = new Container<Diagnostic>(results)
        });
        return Unit.Value;
    }
    
    public TextDocumentOpenRegistrationOptions GetRegistrationOptions(
        TextSynchronizationCapability capability, ClientCapabilities clientCapabilities)
        => new TextDocumentOpenRegistrationOptions();
}
```

2. **`QmuiDidChangeHandler.cs`** — implements `IDidChangeTextDocumentHandler`

   SyncKind = `Full`. Debounce via `CancellationTokenSource` per document URI.
   On each change, cancel previous and schedule new after 300ms.

```csharp
class QmuiDidChangeHandler : IDidChangeTextDocumentHandler
{
    readonly IQmuiDiagnosticService _diagnostics;
    readonly ILanguageServer _server;
    readonly ConcurrentDictionary<Uri, CancellationTokenSource> _debounce = new();
    
    public TextDocumentChangeRegistrationOptions GetRegistrationOptions(
        TextSynchronizationCapability capability, ClientCapabilities clientCapabilities)
        => new() { SyncKind = TextDocumentSyncKind.Full };
    
    public async Task<Unit> Handle(DidChangeTextDocumentParams request, CancellationToken ct)
    {
        // Cancel previous debounce for this document
        if (_debounce.TryRemove(request.TextDocument.Uri, out var previous))
            previous.Cancel();
        
        var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);
        _debounce[request.TextDocument.Uri] = cts;
        
        try
        {
            await Task.Delay(300, cts.Token);
            var results = await _diagnostics.GetDiagnosticsAsync(
                request.TextDocument.Uri.LocalPath,
                request.ContentChanges.First().Text,
                cts.Token
            );
            _server.TextDocument.PublishDiagnostics(new PublishDiagnosticsParams
            {
                Uri = request.TextDocument.Uri,
                Diagnostics = new Container<Diagnostic>(results)
            });
        }
        catch (TaskCanceledException) { /* debounce cancelled, nothing to do */ }
        
        return Unit.Value;
    }
}
```

3. **`QmuiDidCloseHandler.cs`** — implements `IDidCloseTextDocumentHandler`

   Publish empty diagnostics list to clear squigglies. Clean up any debounce state.


4. **`Program.cs` (final)** — DI registration + workspace init

```csharp
using OmniSharp.Extensions.LanguageServer.Server;
using QuickMarkup.LanguageServer.Contracts;
using QuickMarkup.LanguageServer.Diagnostics;
using QuickMarkup.LanguageServer.Handlers;
using QuickMarkup.LanguageServer.Workspace;

await LanguageServer.From(options => options
    .WithInput(Console.OpenStandardInput())
    .WithOutput(Console.OpenStandardOutput())
    .WithHandler<QmuiDidOpenHandler>()
    .WithHandler<QmuiDidChangeHandler>()
    .WithHandler<QmuiDidCloseHandler>()
    .WithServices(services =>
    {
        services.AddSingleton<IRoslynWorkspaceManager, RoslynWorkspaceManager>();
        services.AddSingleton<IQmuiDiagnosticService, QmuiDiagnosticService>();
    })
    .OnInitialize(async (server, request, ct) =>
    {
        var initOpts = request.InitializationOptions as Newtonsoft.Json.Linq.JObject;
        var workspaceRoot = (string?)initOpts?["workspaceRoot"];
        var csprojPath = ProjectFinder.FindCsproj(workspaceRoot);
        if (csprojPath is not null)
        {
            var workspace = server.Services.GetRequiredService<IRoslynWorkspaceManager>();
            await workspace.TryLoadAsync(csprojPath);
            workspace.WatchProjectChanges(csprojPath);
        }
    })
);
```

### Decided

1. **LSP framework: OmniSharp**

2. **Project discovery: VS Code workspace root**

4. **Diagnostics: keystroke with debounce**

### Why keystroke diagnostics is safe (answer to your question)

You asked whether MSBuildWorkspace behaves like the Roslyn analyzer's Compilation
updates. The answer is:

**The Roslyn analyzer gets a new Compilation on every C# keystroke** — but that
doesn't matter for `.qmui` diagnostics because the `.qmui` file isn't a C# source
file. The `QuickMarkupAnalyzer` runs on `CompilationAction`, which only fires
periodically (not per-keystroke for AdditionalFiles).

**In the LSP server, the Compilation is loaded once via MSBuildWorkspace and
cached.** Editing a `.qmui` file does NOT change the `.csproj` or `.cs` files,
so the Compilation stays valid. We only need to re-parse the `.qmui` content and
re-run the binder — both are fast operations (~5-50ms).

So the approach is:
- `.qmui` keystroke → re-parse + re-bind against cached Compilation → publish diagnostics
- `.csproj` change → reload MSBuildWorkspace (rare)
- C# file change → stale diagnostics accepted for Phase 1

No debounce needed for compilation, but a 300ms debounce on the re-parse is still
good practice to avoid wasted work during fast typing.
